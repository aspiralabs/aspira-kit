**Decision:** "We need to make this an infinite pagination scroll page."
## Intent
People can reach every recipe they are permitted to see in Explore and the other search-backed lists, beyond the current ten-result limit, in a predictable order without repeated cards or stale results.
## Problem
Both `/api/v1/search` SQL branches have `LIMIT 10` and no cursor or deterministic tie-break (`apps/web/app/api/v1/search/route.ts:97-120`). Search-backed Explore, profile recipe lists, My Recipes and recipe pickers therefore cannot retrieve further matches. My Recipes also needs a nonempty-result list: its current component fetches results but renders only loading and empty states (`apps/web/app/(app)/recipes/me/my-recipes-content.tsx:18-47`). The profile cookbook tab instead reads `/api/v1/users/{id}/cookbooks`, which currently returns all permitted cookbooks without this ten-result cap (`profile-content.tsx:33-38`; `users/[id]/cookbooks/route.ts:13-30`). Empty-query relevance does not provide the intended predictable default Explore order.
## Change
### API
- Add opt-in cursor pagination to `/api/v1/search`: new clients send `paginated=1`, with `limit` defaulting to 24 and capped at 48, and receive `{ items, nextCursor }`. Keep `apiPaginated` and its `{ data, pagination }` page-based contract unchanged; add a cursor response helper. A request without the new opt-in retains the existing capped bare-array behavior, including unauthenticated mine requests. Keep that compatibility path until the minimum supported installed mobile version uses paginated requests and every remaining web array consumer has migrated; `legacy=1` is not a substitute because installed clients do not send it.
- Support `relevance` by default for nonempty `q` and `newest` by default for empty `q`; also support `top` and `time`. Public relevance uses the current approved snapshot title and existing nutrition boost; mine/admin relevance uses live title. Preserve matching: public `q` searches approved snapshot `searchText` (including its title, preview, description, tags and recipe-line ingredient name, falling back to linked ingredient name when the line name is absent); mine/admin `q` searches live Recipe.title only. `top` orders by Recipe.rating DESC, Recipe.ratingCount DESC, [Recipe.id](http://Recipe.id) DESC. Public `time` sorts and displays approved snapshot prep/cook times; mine/admin use live values. For `time`, a missing prep or cook time places the item after items with both times, followed by total minutes ASC and id ASC; the cursor includes missing-time rank, total when present and id. `newest` orders by Recipe.createdAt DESC, [Recipe.id](http://Recipe.id) DESC in public, mine and admin modes; its cursor holds createdAt and id. *Decision 2026-09-30 (R4): creation order, not publication recency, so a republished recipe keeps its place and paging stays stable.*
- Every sort uses a deterministic id tie-break and a cursor containing every value used by its comparison. Validate cursor structure and its query, sort, filters, mode and viewer scope; malformed or mismatched cursors and unknown sorts return 400. A nonnumeric or below-one limit uses the default 24; values above 48 clamp to 48. Do not treat a cursor as authorization: each page reapplies current session/role, ownership, public visibility, current approved snapshot, takedown and mutual-block rules. Public pages never expose pending working-copy edits. Changes in authorization or visibility invalidate displayed pages; a mine/admin cursor cannot be replayed as another viewer or after losing access. Preserve the current public-only behavior for nonstaff and `onlyPublic` requests, live working-copy behavior for authorized mine/admin requests, and an empty result for unauthenticated mine requests.
- Replace `/api/v1/users/{id}/cookbooks` with a cursor-paginated response: `cursor` and `limit` (default 24, max 48, same clamping as search), returning `{ items, nextCursor }` with the existing item fields. Order stays Cookbook.updatedAt DESC with [Cookbook.id](http://Cookbook.id) DESC as tie-break; the cursor holds updatedAt and id and is bound to the profile id and the viewer's visibility scope, so a cursor minted under owner/SUPER_ADMIN scope returns 400 for any other viewer. Every page reapplies the current rule: owner and SUPER_ADMIN see private and public cookbooks, everyone else sees public only. The web profile cookbook tab is the only consumer (no mobile or other caller), so the response changes directly with no bare-array compatibility path. A cookbook edited while someone is paging can move to the front; clients dedupe by id so it never appears twice. *Decision 2026-09-30 (S2-1): paginate the cookbook endpoint in this release.*
- Use a cursor-aware web fetcher mode or separate hook that sends `cursor` and reads `{ items, nextCursor }`; preserve existing `useInfiniteFetcher` callers that send `page` and read the page-based envelope. Update the search route description.
### Web
- Explore parses and validates `sort` in `app/(app)/recipes/page.tsx`, passes it to `recipes-content.tsx`, and forwards it on every paginated search request. Use an `@aspiralabs/ui` sort control next to the filters. Updating sort preserves existing `q`, cuisine, course, fullMacros and diet URL parameters; reload, shared links and back/forward navigation restore the selection. A query, filter or sort change starts at page one and excludes late responses from the former list.
- Explore and the profile recipe tab append search pages without duplicates and show next-page loading and an exhausted state. The profile recipe list must observe its actual ScrollArea; the planner picker must observe its own scroll container, including when the first page does not fill it. Stop requesting when `nextCursor` is null. Initial failure offers retry rather than an empty/end state; next-page failure retains loaded rows and offers retry without duplicating them. Loading must not issue duplicate page requests.
- My Recipes renders a nonempty scrollable recipe-card list and retrieves all owned pages. The web planner picker's mine and public tabs retrieve all eligible search pages; changing tab or debounced query clears prior pages and prevents late results from becoming visible or selectable. Preserve Enter/Space selection of appended picker results and the intended add-recipe action; loading, failure and exhausted status must not cover its result controls. Migrate the admin featured-recipes search consumer to the opt-in response or retain its bare-array request during compatibility.
- The profile cookbook tab is not fed by `/search` and must not use the recipe search request. It pages the cursor-paginated `/users/{id}/cookbooks` with the same cursor-aware fetcher, observing its ScrollArea, with next-page loading, retry on failure and an exhausted state; owner/SUPER_ADMIN versus public privacy rules are unchanged.
- Isolate accumulated pages and in-flight results by viewer, including anonymous viewers, and by query, sort and filters. On login, logout, account switch, block/unblock or changed access, discard affected search/profile/mine/picker pages before displaying results for the new access state; previously visible private or blocked-author recipes must disappear. Keep sentinel and status outside RecipeCard links, preserve anonymous cards without save controls, and do not introduce paging controls inside card links.
### Mobile
- `(tabs)/explore.tsx` uses `useInfiniteQuery` and `onEndReached` for opt-in cursor pages; pull-to-refresh reloads page one for the current query, filters and sort. Sort chips are included in both the request and query identity. Changing a chip, query or filter abandons old pages and cursors; late old responses cannot append. Prevent duplicate end-reached requests; retain visible rows and offer retry on a later-page failure, distinguish first-page failure from an empty result, and show exhaustion only after a successful terminal page. The selected sort lives in Explore's route params (`sort`), like `course` already does: choosing a chip writes it with `router.setParams`, returning to Explore or opening a link with `?sort=` restores it, and a missing or unknown value falls back to the default (`newest` for empty `q`, `relevance` otherwise). *Decision 2026-10-02 (replaces R6): keep sort in the route so it is restorable and linkable (TS-025).*
- `user/[id].tsx` paginates its recipe list. Both mine and Explore tabs of the mobile meal-plan recipe picker paginate `/search` as their lists scroll, reset on tab/query changes and prevent stale results from crossing tabs. Installed pickers that have not migrated continue to receive bare arrays during the compatibility window.
- Query identity or an account-change cache reset must isolate anonymous and signed-in viewers. Login, logout, account switch and block/unblock discard affected cached and in-flight search/profile/picker pages before display; block/unblock invalidation includes `['search']` as well as existing recipe views.
## Out of scope
Filters beyond sort (see `_12_search-filters/spec.md`).
## Acceptance criteria
### Features
- [ ] F1: An opted-in search for seven seeded eligible recipes at `limit=2` returns two items per full page; following each `nextCursor` reaches all seven exactly once, including across equal sort values, and the final page has `nextCursor: null`. A request without the opt-in still returns the legacy capped bare array, including to an older installed mobile client and unchanged web array consumers.
- [ ] F2: For every supported sort, pages follow its documented comparison including id ties. Empty `q` defaults to `newest` and nonempty `q` to `relevance`; `top` handles equal default-zero ratings and counts, and `time` handles tied totals and either missing time without repeats. Public time order and displayed times use approved snapshots even after an unapproved time edit; mine/admin use live times. A public ingredient-only snapshot match remains findable on later pages, while mine/admin title-only matching is not represented as ingredient matching. `newest` orders by recipe creation time, newest first, with id ties; republishing a recipe does not move it.
- [ ] F3: `limit=500` yields no more than 48 items; absent, nonnumeric or below-one limits use 24. Malformed cursors, cursors reused with another query, sort, filters, mode or viewer, and unknown sorts receive 400. Changing sort or filters never appends results from the old cursor.
- [ ] F4: Across pages, signed-in mine results contain only that viewer's live recipes; unauthenticated mine returns an empty paginated result with `nextCursor:null`. Authorized staff admin results obey their live admin mode, while nonstaff and `onlyPublic` pages expose only currently eligible approved public content, never drafts or unapproved edits. Subsequent requests reapply current visibility, takedown, block and role rules; revoked items disappear from an open list, remaining accessible items can still be paged without duplicates, and a former mine/admin cursor grants no access after viewer or role change.
- [ ] F5: With 30 public recipes, web Explore loads the first page, requests further pages when its sentinel reaches the end, displays all 30 once and then displays exhaustion. Sorting a filtered search preserves `q`, cuisine, course, fullMacros and diet in the URL; a shared URL, reload and back/forward restore sort and filters. Changing query, sort or filters starts again at page one and excludes late prior responses.
- [ ] F6: The web profile recipe tab reaches every eligible recipe beyond the first page within its ScrollArea. With 30 owned recipes, My Recipes renders all 30 as recipe cards without duplicates, including when its first page is nonempty. Each page stops requesting at exhaustion, including when the first page does not fill its scroll container. With more than one page of cookbooks, the profile cookbook tab reaches every cookbook once: the owner and a SUPER_ADMIN reach all private and public cookbooks across pages, any other viewer reaches only public ones, and no page leaks a private cookbook. A cursor from an owner session reused by another viewer returns 400.
- [ ] F7: Each web planner-picker mine/public tab can scroll its modal list through all eligible matching recipes. Tab and query changes remove old rows and prevent late results from appearing or being selected; Enter/Space still selects an appended row and adds the intended recipe. A failed first or later page offers retry; later-page failure preserves valid rows, retry continues without duplicates, and loading/exhausted status does not obstruct selectable rows.
- [ ] F8: With 30 eligible public recipes, mobile Explore reaches all 30 once through `onEndReached`. A chip change after several pages restarts the active query and filters at page one in the new sort; pull-to-refresh restarts page one in the currently selected sort. Loading prevents duplicate requests, a first-page error offers retry rather than masquerading as empty, a later-page error retains rows and offers retry, and exhaustion appears only after a successful final page. The selected sort is kept in Explore's route: returning to Explore or opening a link with `?sort=` restores it, and a missing or unknown value uses the default.
- [ ] F9: The mobile profile recipe list reaches later eligible pages. Both mine and Explore tabs of the mobile meal-plan picker reach later pages, reset on tab or query change, and never show stale results from the other tab. An older installed picker still receives its bare-array response.
- [ ] F10: After login, logout or switching between two accounts, web and mobile search-backed lists do not display or append another viewer's private pages; anonymous views never reuse authenticated pages. After block/unblock or a visibility/access change, affected Explore, profile, mine and picker rows are revalidated before display, blocked or hidden recipes disappear, and in-flight old responses cannot restore them.
- [ ] F11: In the web card grid, keyboard focus reaches each recipe navigation link and any separate action independently; Enter activates only the focused control. The paging sentinel and status are outside card links, and anonymous cards expose no save action.
The original seven-row cursor, tied-sort, `limit=500`, malformed-cursor, 30-row scrolling, sentinel and mobile refresh scenarios above are planning inputs for the planner's feature-mapped checks, not a separate technical test checklist.
